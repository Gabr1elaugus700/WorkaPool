## Problem Statement  Gestores e vendedores do WorkaPool não têm uma visão única e rápida do relacionamento comercial com um cliente. Hoje as informações estão espalhadas (consultas no Senior, Order Loss, clientes inativos, Power BI), exigem ir ao SQL Server em horário comercial e não formam uma tela de análise para decidir "como está este cliente?" em poucos segundos.  ## Solution  Entregar o **Customer Overview** (visão 360º do cliente): uma listagem/busca de carteira e uma tela por cliente (`:clienteId`) alimentada por um **read model no Postgres do WorkaPool**, preenchido por um **worker noturno** que executa as consultas Senior já validadas e materializa agregados por seção.  A abertura da tela é leve (identidade + resumo + metadados de sync); evolução, produtos e pedidos recentes carregam sob demanda. Order Loss, clientes inativos e Power BI continuam existindo — o Overview **compõe** com deep-links, sem absorvê-los.  ---  ## User Stories  1. As a gestor, I want to open a customer's commercial overview, so that I can understand the relationship quickly without querying the ERP myself. 2. As a vendedor, I want to see only customers where I am the primary salesperson, so that I focus on my portfolio. 3. As an ADMIN or Gerente, I want to open any customer's overview, so that I can support the team and audit relationships. 4. As a vendedor or gestor, I want to search customers by code, trade name, or CNPJ/CPF, so that I can find the right account fast. 5. As a vendedor or gestor, I want a paginated portfolio list sorted by order activity (last 12 months) by default, so that active accounts surface first. 6. As a user, I want to change list sort (e.g. last purchase, revenue), so that I can explore the portfolio differently. 7. As a user, I want list columns for code, name, city/UF, branch indicator, last purchase, 12-month revenue, and days since last purchase, so that I can triage before opening the detail. 8. As a user, I want to open `/overview/customers/:clienteId`, so that I land on that customer's overview. 9. As a vendedor blocked from another rep's customer, I want a clear access-denied view with a path back to the list, so that I am not left on a broken screen. 10. As a user, I want to see when data was last successfully synced, so that I know how fresh the overview is. 11. As a user, I want customer identity (code, trade name / fantasia, document, city/UF, segment, registration date, primary `codRep`, first/last invoiced purchase, branch indicator), so that I confirm I am looking at the right account. 12. As a user, I want a branch indicator (MGA, CTB, or both when both have activity), without ranking one branch over the other, so that I know which units serve the account. 13. As a user, I want commercial summary KPIs (revenue total since 2024 cutoff, revenue last 12 months, invoiced order counts, average ticket, volume, weighted average margin %, purchase frequency days, days since last purchase), so that I grasp the commercial posture at a glance. 14. As a user, I want UI copy that states metrics are "since Jan/2024" where totals apply, so that I do not confuse cutoff totals with all-time ERP history. 15. As a user, I want monthly evolution (revenue, volume, order count, margin when available), so that I see growth, stability, or decline. 16. As a user, I want top purchased products with quantity, volume, revenue, average price, margin, first/last purchase, frequency, and revenue share, so that I understand the mix. 17. As a user, I want a short summary of invoiced vs lost orders in the last 12 months plus last dates, so that I see recent commercial motion. 18. As a user, I want the 5 most recent invoiced orders, so that I can inspect recent wins without loading full history. 19. As a user, I want the 5 most recent lost orders (`sitped = 5`), so that I can inspect recent losses consistent with Order Loss. 20. As a user, I want separate fields for last invoiced purchase, last lost order, and last commercial movement (max of invoiced and lost dates), so that frequency and risk are not ambiguous. 21. As a user, I want frequency shown as average days between purchases and days since last purchase (no traffic-light status yet), so that I can judge the cycle myself. 22. As a user, I want deep-links to Order Loss / related existing tools where useful, so that I deepen analysis without duplicating those products. 23. As an ADMIN, I want a sync admin view with run/step logs, errors, counts, and last success, so that I can operate the overnight pipeline. 24. As an ADMIN, I want to force a retry of the sync pipeline or a failed step at any time, so that I can recover without waiting for the next night. 25. As the system, I want overnight sync with per-step retries (max 3) and atomic publish of a full successful snapshot, so that daytime API traffic never hits Senior for this overview. 26. As the system, I want to keep serving the last good snapshot if tonight's sync fails, so that users are not blocked by a bad run. 27. As a developer, I want vertical slices (sync → identity/auth → list → summary → monthly → products → recent orders → frequency numbers), so that each increment is shippable end-to-end. 28. As a developer, I want parity tests against known Senior SQL results for a fixture customer, so that the read model does not silently drift from trusted queries.  ---  ## Implementation Decisions  ### Bounded context and seams  - New bounded context: **Overview Customer** (code/API naming `overview_customer` / `/api/overview/...`), separate from Pedidos cargo, Order Loss negotiation, and legacy flat Sapiens routes. - **Primary test seam (one high seam):** the Overview Customer application boundary — (1) sync pipeline outcomes written to the read model, (2) HTTP API responses under auth. Prefer feeding the sync with recorded Senior query results / FakeSapiens-style doubles rather than asserting SQL text or Prisma internals. - Reuse existing vocabulary: Cliente (`codcli`), Pedido (`numped`, `sitped`), `codRep`, NF faturada filters already used in commercial queries, Order Loss meaning of perdido (`sitped = 5`). - Do not extend legacy root `controllers/services/repositories` for this feature; follow feature-folder vertical slices (same family as Order Loss / Goals).  ### Data architecture  - Senior Sapiens remains system of record for ERP facts. - WorkaPool Postgres holds the **analytics read model** for Overview; user requests read only Postgres (+ Redis is out of scope). - Nightly scheduled worker runs the validated SQL scripts (identity, commercial summary, monthly evolution, products, recent orders), transforms into overview tables, does **not** run heavy sync inside user HTTP requests. - Sync shape: orchestrated **pipeline with steps**; **retry up to 3 times per step**; publish/swap to production read tables only when the required steps succeed; on failure, retain previous successful snapshot and record errors. - ADMIN-only sync operations UI/API: list runs/steps, errors, record counts, `lastSuccessfulSyncAt`, trigger retry (pipeline or step).  ### Read model tables (conceptual)  - `overview_customer` — identity + portfolio keys (incl. primary `codRep`, branch indicator flags/labels) - `overview_customer_summary` — commercial KPIs - `overview_customer_monthly` — monthly series - `overview_customer_product` — product aggregates - `overview_customer_recent_order` — recent invoiced/lost rows (typed) - `overview_customer_sync_run` / `overview_customer_sync_step` — operational sync metadata  ### Business rules (canonical)  - **Effective sale / revenue / volume / ticket / frequency base:** NF lines with `sitnfv = 2`, `venfat = 'S'`, `qtdfat > qtddev`, and associated pedido `numped > 0` (as in existing analysis SQL). - **History cutoff:** persist and compute from `2024-01-01`; "total" means since cutoff, labeled in UI. - **Volume:** `qtdfat - qtddev`; product code `101072` uses half volume (`/ 2`) as documented business rule. - **Margin:** item field `usu_mgmluc` as **percent**; always aggregated from **items**, **weighted by line revenue** (not average-of-order-averages). - **Lost order:** ERP `sitped = 5` (same source semantics as Order Loss Sapiens pull). App-only Order Loss motivos are not required for MVP recent-lost list. - **Primary salesperson:** same rule as summary SQL — `codRep` with most invoiced orders since cutoff; tie-break last sale date. Used for VENDAS authorization. - **Dates:** keep separate last invoiced purchase, last lost order; last commercial movement = max of those two dates. - **Branch indicator:** derive from activity (`codfil` 1 → MGA, else CTB); show MGA, CTB, or both; **no** primary-branch ranking. - **Identity:** trade name from `apecli` (fantasia); first/last purchase use invoiced-NF rules (not unfiltered NF subqueries). Status/razão social only if clearly available — MVP keeps minimal identity.  ### Authorization  - VENDAS: only customers where user `codRep` equals overview primary `codRep`. - ADMIN and Gerente: all customers. - Unauthorized `:clienteId`: HTTP 403 + simple access-denied UI (back to list). Polished dedicated page can follow later.  ### API / UX contracts  - List: `GET /api/overview/customers` — search by exact code OR name/fantasia contains OR document; default sort **order count last 12 months desc**; page size 20; portfolio scoping as above. - Detail first paint: `GET /api/overview/customers/:clienteId` — identity + summary + `lastSuccessfulSyncAt` (+ section availability flags). - Lazy: monthly, products, recent orders via dedicated GETs under the same prefix. - Admin sync: `/api/overview/sync/...` (ADMIN only). - Frontend routes: list page preceding `:clienteId` overview page. - Compose with existing products via links; do not merge Order Loss Kanban or Power BI into this screen.  ### Delivery slices (order)  1. Sync infra + admin logs/retry   2. Identity + auth   3. Customer list/search   4. Commercial summary   5. Monthly evolution   6. Products   7. Recent invoiced + recent lost + movement date fields   8. Frequency numbers on summary (no cycle traffic light)  ### Source SQL (inputs to sync design)  Trusted scripts already authored for analysis (identity, commercial summary, monthly evolution, products, last order exploration). Sync implementation must preserve their commercial filters; identity/last-purchase paths must be aligned to invoiced-NF rules where the grill overruled older subquery behavior.  ---  ## Testing Decisions  - Test **external behavior** at the Overview seam: given fixture Senior extract / double, after sync the read model and API return the expected overview for a customer; auth denies cross-portfolio VENDAS; admin retry transitions sync run state correctly. - Do **not** treat private SQL string assembly or ORM calls as the unit under test. - **Gate for first sync slice:** idempotent rebuild; step failure → ≤3 retries → failed run; successful swap only on success; `lastSuccessfulSyncAt` does not advance on failure; admin can trigger retry; **numeric parity** for at least one fixture customer against the trusted Senior summary SQL. - Cover empty customer, extreme volumes, product `101072` volume rule, weighted margin example, lost vs invoiced date separation, dual-branch indicator. - Prior art: `FakeSapiens` and feature tests around Order Loss / pedidos; mirror that style for Overview doubles and HTTP contract tests. - Frontend: first paint shows summary without waiting for lazy sections; 403 shows access-denied affordance.  ---  ## Out of Scope  - Automatic commercial "opportunities" engine   - Stagnant/abandoned open-order classification and thresholds   - Full order history explorer, item drill-down of all history, export   - Redis cache layer   - Risk ranking / "customers to call" list sort as default product   - Purchase-cycle traffic light (within / near / outside)   - Absorbing or replacing Order Loss, clientes inativos, or Power BI   - Live per-request queries to Senior for Overview pages   - Weighted-vs-simple margin dual display (only weighted-by-line-revenue)   - Primary-filial ranking   - Deep merge of Order Loss app `LOST` motivos into MVP lost list    ---  ## Further Notes  - Origin: grilled from initial Customer 360º PRD draft; decisions locked in session (architecture = nightly sync into WorkaPool Postgres). - MVP job-to-be-done: **understand the commercial relationship**; seller "call now?" risk workflows are secondary and partly deferred (risk list slice later). - Access-denied polished page and cycle semaphore remain explicit follow-ups. - Label UI totals as since Jan/2024 to avoid false "all-time" reading. - When implementing, keep Senior load off business hours; ADMIN forced retry is the only daytime sync trigger and must remain asynchronous.
